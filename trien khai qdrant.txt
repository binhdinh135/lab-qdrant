│  INPUT (Qdrant NHẬN):                                        │
│  • Dense vector (1024 số thực) – semantic meaning            │
│  • Sparse vector (keyword weights) – keyword matching        │
│  • Payload (JSON metadata)                                   │
│  • ID (định danh)                                            │

│  PROCESS (Qdrant XỬ LÝ):                                    │
│  • Xây HNSW graph cho dense vectors                          │
│  • Xây inverted index cho sparse vectors                     │
│  • Tạo payload indexes (filter nhanh)                        │
│  • Quantize dense vectors (INT8 nếu bật)                     │
├─────────────────────────────────────────────────────────────┤
│  STORAGE (Qdrant LƯU):                                      │
│  Point = {                                                   │
│    id: "chunk-001",                                          │
│    vector: { "dense": [0.12, -0.34, ...],    ← 1024 số      │
│              "sparse": {"nghỉ":0.8,"phép":0.7} ← keywords  }│

│  }                                                           │
├─────────────────────────────────────────────────────────────┤
│  OUTPUT (khi search):                                        │
│  • Top N points gần nhất (semantic + keyword kết hợp)        │
│  • Kèm payload + score                                      │
│  • Đã filter theo payload conditions                         │
└─────────────────────────────────────────────────────────────┘

2.2 Hybrid Search trong Qdrant (thay Elasticsearch)

BGE-M3 sinh cả dense vector VÀ sparse vector cho mỗi chunk:

Dense: hiểu ngữ nghĩa ("nghỉ phép" ≈ "phép năm")

Sparse: bắt keyword chính xác ("QĐ-2024-0123")

Qdrant search cả 2 cùng lúc → fusion nội bộ → Top N

# Search hybrid (dense + sparse) trong Qdrant
results = client.query_points(
    collection_name="smart_search",
    prefetch=[
        Prefetch(query=dense_vector, using="dense", limit=100),
        Prefetch(query=sparse_vector, using="sparse", limit=100),
    ],
    query=FusionQuery(fusion=Fusion.RRF),  # RRF fusion nội bộ
    query_filter=Filter(must=[
        FieldCondition(key="doc_status", match=MatchValue(value="ACTIVE")),
    ]),
    limit=50,
)

→ Không cần Elasticsearch. Qdrant làm cả hai.

7.2 RAM

Giả định: INT8 quantization, Mmap, HNSW m=16, Replica=2, D=1024

Breakdown ước tính (1M vectors, D=1024, INT8 + mmap):

Quantized vectors: 1M × 1024 × 1 byte       ≈ 1.0 GB
HNSW graph:        1M × ~250 bytes           ≈ 0.25 GB
Payload index:     1M × ~200 bytes           ≈ 0.2 GB
────────────────────────────────────────────────────────
Pure data subtotal:                          ≈ 1.5 GB

Runtime overhead (fragmentation, cache,
  segment management, optimizer):            ≈ 2-4 GB
────────────────────────────────────────────────────────
Thực tế tiêu thụ:                            ≈ 4-6 GB / 1M vectors

Để capacity planning theo hướng bảo thủ, tài liệu sử dụng 6 GB/1M vectors(cận trên, dự phòng peak và runtime overhead).

Bao gồm:

Quantized vectors (INT8)

HNSW graph

Metadata/payload index overhead

Runtime overhead (fragmentation, segment management, cache)

Không bao gồm: OS, page cache, monitoring (tính riêng bên dưới).

Cluster RAM ≈ (Vectors / 1M) × 6 GB × Replication Factor
            + 8 GB (OS + page cache + monitoring cho toàn cluster)

Lưu ý: Replica không tăng RAM trên 1 node, mà tăng RAM toàn cluster (mỗi node hold thêm replica data).

Ví dụ: 10M vectors, replica=2:

Cluster RAM = 10 × 6 × 2 + 8 = 128 GB ≈ 130-150 GB (làm tròn bảo thủ)
→ 5 VMs × 32GB hoặc 4 VMs × 48GB

7.3 SSD

~5-6 KB/vector (1024d), tương đương ~11 GB cluster SSD / 1M vectors (đã bao gồm replica=2).Production khuyến nghị cấp phát 2.5-3× actual (WAL, snapshot, segment merge, growth).

Cluster SSD (R=2) ≈ (Vectors / 1M) × 11 GB
SSD khuyến nghị   ≈ Cluster SSD × 2.5-3

Ví dụ: 10M vectors:

Cluster SSD (R=2) = 10 × 11 = ~110 GB
SSD khuyến nghị  = 110 × 2.5-3 = ~275-330 GB → cấp 300 GB cluster

PHẦN C – CHIẾN LƯỢC SHARD & REPLICA (chi tiết)

9. Kiến trúc phân tán Qdrant

9.1 Cấu trúc phân cấp

Qdrant Cluster
  └── Collection "smart_search"
        ├── Named vectors: "dense" (1024d) + "sparse"
        ├── 4-8 Shards (chia ngang data)
        │     └── 2 Replicas/shard (Replication Factor = 2)
        │           └── Segments (auto-managed)
        └── Payload indexes (doc_status, domain, departments)

9.2 Shard – tại sao cần?

1 node (không cluster)

Multi-node cluster (4 nodes)

10M vectors trên 1 node → RAM ~130GB

Chia 4 shards = 2.5M/shard → ~32GB/node

Throughput bị giới hạn 1 CPU

Search song song 4 shards

Single point of failure

HA: mất 1 node → cluster vẫn phục vụ

Cho 10M vectors: khuyến nghị 4-8 shards để cân bằng giữa:

Parallel search (cải thiện khả năng xử lý song song; quá nhiều shard có thể tăng merge overhead)

RAM/node (ít shard = mỗi node chứa nhiều hơn)

Metadata overhead (quá nhiều shard = overhead quản lý tăng)

Khuyến nghị ban đầu: 4 shards (1 shard/node trên cluster 4 nodes).Có thể tăng lên 8 shards nếu cần scale throughput sau go-live.

9.3 Replica – tại sao cần?

Mỗi shard có 2 replicas (Replication Factor = 2), được phân bố trên các node khác nhau để đảm bảo High Availability. Việc ghi được điều phối bởi cơ chế đồng thuận và đồng bộ dữ liệu của Qdrant Cluster.

Khi một node gặp sự cố:

Replica còn lại trên node khác tiếp tục phục vụ shard

Cluster tự đồng bộ lại khi node phục hồi hoặc node mới tham gia

Query có thể được phân phối tới các replica của shard để tăng khả năng xử lý đọc và cân bằng tải

12. Search song song & Failover

12.1 Search fan-out

Query → Qdrant Cluster
    ├──► Shard 0 (node 1): search 2.5M vectors → top 100
    ├──► Shard 1 (node 2): search 2.5M vectors → top 100
    ├──► Shard 2 (node 3): search 2.5M vectors → top 100
    └──► Shard 3 (node 4): search 2.5M vectors → top 100
              │
              ▼
        Merge 400 results → top 100 (highest score)

top 100 chỉ là ví dụ, phụ thuộc tham số limit của truy vấn.

12.2 Failover

Node 2 gặp sự cố:→ Replica còn lại của các shard trên node khác tiếp tục phục vụ→ Cluster tự đồng bộ lại khi node 2 phục hồi hoặc node mới tham gia→ Truy vấn không bị gián đoạn

15. Ingestion Pipeline

from qdrant_client.models import PointStruct, SparseVector
import uuid

def ingest(client, chunks, embed_model, batch_size=200):
    buffer = []
    for chunk in chunks:
        dense, sparse = embed_model.encode(chunk["text"])  # BGE-M3 → both
        buffer.append(PointStruct(
            id=str(uuid.uuid4()),
            vector={"dense": dense.tolist(), "sparse": sparse},
            payload={
                "document_id": chunk["doc_id"],
                "title": chunk["title"],
                "text": chunk["text"],
                "domain": chunk.get("domain", "general"),
                "doc_status": "ACTIVE",
                "allowed_departments": chunk.get("depts", ["ALL"]),
                "has_user_acl": chunk.get("has_user_acl", False),
            },
        ))
        if len(buffer) >= batch_size:
            client.upsert("smart_search", points=buffer)
            buffer = []
    if buffer:
        client.upsert("smart_search", points=buffer)

Throughput: batch=200 → ~5.000-10.000 pts/s

16. Search Integration

from qdrant_client.models import *

def search(client, query_text, embed_model, user_depts, top_k=100):
    dense, sparse = embed_model.encode(query_text)
    
    return client.query_points(
        collection_name="smart_search",
        prefetch=[
            Prefetch(query=dense.tolist(), using="dense", limit=200),
            Prefetch(query=SparseVector(**sparse), using="sparse", limit=100),
        ],
        query=FusionQuery(fusion=Fusion.RRF),
        query_filter=Filter(must=[
            FieldCondition(key="doc_status", match=MatchValue(value="ACTIVE")),
            FieldCondition(key="allowed_departments",
                          match=MatchAny(any=user_depts + ["ALL"])),
        ]),
        limit=top_k,
        with_payload=True,
    )

PHỤ LỤC

A. Kiến thức nền

Vector/Embedding: Text → mảng N số (N = dimension). Texts cùng ý nghĩa → vectors gần nhau.

HNSW: Graph algorithm tìm nearest neighbor nhanh (~50ms cho 10M vectors thay vì ~10s brute force). Trade-off: approximate (~99% recall).

Scalar Quantization: Nén float32 → int8. Giảm RAM 4x, mất <1% recall.

Sparse Vectors: Giống BM25 inverted index nhưng dưới dạng vector. Bắt keyword chính xác.
